## 1. The question

Does ranking large caps by 63-day relative strength, holding the top 10% for
10 trading days, and exiting at a 2.5 × ATR(14) stop pick stocks that beat
**random stocks bought on the same days and held for the same number of bars**?

This is a question about selection. The same-day benchmark
(`date_matched_benchmark`) keeps each trade's calendar and swaps only the
symbol, so timing can't count as selection skill.

## 2. The configuration, and how it was chosen

The configuration is the plateau centre of the `h1_exits` surface in the
2026-09-18 development battery. It was selected by docs/03 §0.7, the project's
existing rule, and not by the drafter:

| option | value | source |
| --- | --- | --- |
| hold | 10 | h1_exits plateau centre |
| stop_atr | 2.5 | h1_exits plateau centre |
| rs_lookback | 63 | `backtest run` default, which h1_exits held fixed |
| top_pct | 0.10 | `backtest run` default, which h1_exits held fixed |
| trend_filter | on | default |
| use_stop | yes | default |
| entry_delay | 1 (next open) | the original rule, written out explicitly |
| equity, slippage | $10,000, 5 bps each side | defaults |

**Not registered, and why:**

- **The best-looking H1 cell**: `rs_lookback=252, top_pct=0.10`, at the 97th
  percentile on the same-day benchmark. It is the *peak* of the `h1_selection`
  surface, and §0.7 rejects peaks.
- **The `h1_selection` plateau centre** (`rs_lookback=126, top_pct=0.20`). Its
  profit factor is 1.099 on development, below the 1.20 bar. It fails before
  validation.
- **The no-stop variant.** Its 2.9 SE advantage was measured in the isolated
  $5M portfolio at a 20-bar limit. In the tradeable portfolio at a 10-day hold,
  removing the stop makes H1 *worse*: +0.005R and profit factor 1.095
  (`h1_no_stop`, hold=10). The exit finding doesn't carry over to this
  configuration.

The hold is written out explicitly, so this registration's hash doesn't depend
on `HOLD_DEFAULTS["h1"]`. That default moved from 5 to 20 on 2026-09-18, after
this configuration was chosen, and the registration is unaffected.

## 5. The test

**Split:** validation, 2016-01-01 to 2019-12-31, and nothing else. **One
configuration**, leaving two of H1's three validation slots unspent.

**Pass requires all of:**

1. Every criterion in `backtest/performance.py`, as the code applies it.
2. **Same-day percentile ≥ 95th.** This is in the `[decision]` block below.
   Once signed, `backtest run` applies it and counts it toward pass/fail.
   *The operator should keep it or delete it before signing, not after.*
   - Why add it: the existing 75th-percentile bar passes a rule with no
     selection skill one time in four. The 95th is the usual one-sided 5% level
     for a single pre-registered test, and it isn't adjusted for the other six
     hypotheses (that's open decision 5).
   - This configuration reached the 94.7th on development, so it would narrowly
     fail this bar even in-sample. That's intended: the bar is set by what
     counts as evidence, not by what the candidate achieved.

## 6. Two problems with the test as it stands

**The regime criterion requires every validation regime to be positive.**
docs/03 §0.6 says "positive in ≥ 3 of 5 buckets", but no split contains five.
Validation contains exactly three: bull 2017, **the 2018-Q4 correction**, and
bull 2019. So in practice the criterion asks a long-only rule to finish
positive through a quarter when the S&P fell about 14%. That gap between the
specification and the code is the operator's to resolve. The resolution would
also be chosen *after* seeing H1 fail regime robustness on development, which
this document records.

**The gates below aren't met.** Delisted coverage isn't fixed, and CLAUDE.md
freezes validation until it is.

## 7. Power, estimated without touching validation

Development ran 566 trades in 6 years, about 94 a year, so validation's 4 years
should produce about **377**. The design effect measured on this configuration
is 1.5 (monthly clusters) and 1.2 (quarterly), giving roughly **250–310
effective observations**. That clears the 200-trade floor whether it's read as
nominal or effective. Too few trades won't be what fails this test.

## 8. What each outcome means, decided now

| outcome | consequence |
| --- | --- |
| passes 1 and 2 | Goes to the test split with **this configuration, unchanged**. One run, once. |
| passes 1, fails 2 | Beat a weak bar but not a conventional one. Recorded as **not validated**. Does not go to test. |
| fails 1 | **Failed validation**, recorded. H1 is closed as a strategy candidate. The two unspent validation slots are **not** to be used on nearby configurations; that would be the search the budget exists to prevent. |

Every outcome is recorded in `research_runs` and CLAUDE.md, including a
failure.

## 9. Why write this down if the advice is not to sign it

Because the configuration is now fixed. Whatever the operator later decides
about regimes, coverage, or the hold period, H1 can't be re-tuned toward
validation without the change showing up as an edit to this file in the git
history. A pre-registration written after those decisions would be picked with
knowledge they add. This one records what was known on 2026-09-18, including
that it fails in-sample.
